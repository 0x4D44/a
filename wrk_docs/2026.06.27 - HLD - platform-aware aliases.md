# Platform-Aware Aliases

Status: SIGNED-OFF

## Intent

One logical alias name should resolve to the preferred command for the platform running `a`, so aliases like `co` and `cl` can stay memorable while using direct invocation on Windows and a tmux wrapper on macOS/Linux.

## Scope

- Add platform-specific command variants to an existing alias.
- Resolve the active command at alias execution time from the current OS.
- Provide CLI commands to add and remove platform variants.
- Update help/README and focused tests for the new behavior.
- Keep default aliases valid: an alias without platform variants behaves exactly as it does today.
- Document the exact setup commands for the current Codex/Claude aliases: `co`, `cor`, and `cl`.

## Out Of Scope

- A built-in tmux session manager or wrapper script.
- Feature flags or environment-variable based selection.
- Migration choreography beyond serde defaults for the new optional JSON field.
- Supporting platforms outside this repo's stated target set: `windows`, `macos`, and `linux`.
- Committing `config.json` entries that point at a missing tmux wrapper. The local machine has `tmux`, `codex`, and `claude`, but no `a-tmux` command on PATH today.

## Approach

Extend `AliasEntry` with a serde-defaulted platform map:

```rust
#[derive(...)]
#[serde(rename_all = "lowercase")]
enum Platform {
    Windows,
    Macos,
    Linux,
}

#[serde(default, skip_serializing_if = "BTreeMap::is_empty")]
platforms: BTreeMap<Platform, CommandType>,
```

`Platform` provides:

- `Platform::current() -> Platform`, mapping `std::env::consts::OS`.
- `Platform::parse(input: &str) -> Result<Platform, String>`, accepting `windows`, `macos`, `linux`, and `current`.
- serde validation for persisted JSON keys, so hand-edited or pulled configs cannot silently keep invalid platform names.

Example JSON:

```json
{
  "aliases": {
    "co": {
      "command_type": {
        "Simple": "codex --dangerously-bypass-approvals-and-sandbox"
      },
      "platforms": {
        "macos": {
          "Simple": "a-tmux codex --dangerously-bypass-approvals-and-sandbox"
        },
        "linux": {
          "Simple": "a-tmux codex --dangerously-bypass-approvals-and-sandbox"
        }
      },
      "description": null,
      "created": "2025-11-18"
    }
  }
}
```

Resolution stays local to `AliasEntry`:

- `command_type_for_platform(platform: Platform) -> &CommandType`
- `active_command_type() -> &CommandType`

Display stays centralized in one `CommandType` formatter. Active/default/platform displays resolve a `CommandType` first and then call that formatter, avoiding duplicate chain formatting logic.

Execution changes from matching `entry.command_type` directly to matching the resolved command type. The public path uses `active_command_type()`. Tests can call `execute_alias_for_platform(name, args, platform)` so override execution is verified without pretending the test runner is another OS. Existing chain execution and parameter substitution stay unchanged because platform variants are still `CommandType`.

Add explicit management commands:

- `a --platform-add <alias> <platform> <command> [same chain options as --add] [--force]`
- `a --platform-remove <alias> <platform>`

`--platform-add` requires the base alias to already exist. That keeps the model simple: `command_type` remains the fallback and every alias always has a default command.

Overwrite rules:

- Re-adding an existing platform variant mirrors `--add`: prompt with current/new values unless `--force` is present.
- Updating a base alias with `--add` or `--force` preserves existing platform variants. There is no clear-all operation in this change; use `--platform-remove` for individual variants.
- `--platform-remove` deletes only the named platform variant and leaves the base alias intact.

Inspection:

- `a --list` shows the active command in the `->` slot. If the current platform is using an override, add a compact marker such as `[platform: macos]`. If variants exist but the current platform is falling back to the default, add `[variants: linux, macos]`.
- `a --which <alias>` shows the active command first, then the default command and platform variants in stable order. It marks the current platform and states whether it is using an override or fallback.
- Parameter examples and chain breakdowns in `--which` use the resolved active `CommandType`.

To avoid duplicating the already-large `--add` parser, extract the shared command-spec parsing into a helper that returns:

- `CommandType`
- optional description
- `force`

The helper is pure and returns `Result<ParsedCommandSpec, String>`; only `main` prints errors and exits. It is used by `--add` and `--platform-add`. For platform variants, `--desc` updates the alias description rather than creating a per-platform description.

Centralize config parsing:

- Add a shared config-content parser used by local load and GitHub pull.
- The parser tries the current schema first, then the existing legacy migration.
- The `Platform` map key type makes invalid platform keys fail fast in both paths.

Concrete alias setup:

- README documents these setup commands once a tmux wrapper command exists:
  - `a --platform-add co macos "a-tmux codex --dangerously-bypass-approvals-and-sandbox"`
  - `a --platform-add co linux "a-tmux codex --dangerously-bypass-approvals-and-sandbox"`
  - `a --platform-add cor macos "a-tmux codex --dangerously-bypass-approvals-and-sandbox resume --last"`
  - `a --platform-add cor linux "a-tmux codex --dangerously-bypass-approvals-and-sandbox resume --last"`
  - `a --platform-add cl macos "a-tmux claude --permission-mode bypassPermissions --system-prompt ."`
  - `a --platform-add cl linux "a-tmux claude --permission-mode bypassPermissions --system-prompt ."`
- `cor` is treated as a Codex interactive alias and gets the same platform preference in documentation.
- The checked-in `config.json` is not changed to use `a-tmux` in this task because that command is not present in this repo or on this machine.

## Acceptance Criteria

- An existing config without `platforms` loads and behaves unchanged.
- `a <alias>` executes the platform override when the current OS has one, otherwise the default `command_type`.
- `a --which <alias>` shows the active command, active parameter examples/breakdowns, and configured platform variants in stable order.
- `a --list` shows the active command in the `->` slot and keeps platform variant visibility concise.
- `a --platform-add co macos "a-tmux codex --dangerously-bypass-approvals-and-sandbox"` stores a macOS variant without replacing the default command.
- Re-running `--platform-add` for an existing alias/platform prompts unless `--force` is passed.
- Re-running `--add` for a base alias preserves any existing platform variants.
- `a --platform-remove co macos` removes only the macOS variant and leaves the base alias intact.
- Invalid platforms are rejected.
- Invalid persisted platform keys fail in both local load and GitHub pull parsing paths.
- README shows exact setup commands for `co`, `cor`, and `cl`.
- Focused tests cover serialization defaults, resolution fallback, override execution, validation, parser reuse, overwrite preservation, and platform add/remove.
- `cargo fmt --all`, `cargo clippy -- -D warnings`, and `cargo test` pass.

## Decision Log

- Keep one logical alias name with an optional per-platform override map, not separate aliases per platform.
- Use exact platform keys only (`windows`, `macos`, `linux`) plus CLI shorthand `current`; skip a `unix` grouping for now because duplicate macOS/Linux entries are simpler than another fallback tier.
- Require a base alias before adding platform variants, so `command_type` remains the default and the config shape stays backward-compatible.
- Keep tmux wrapping outside this change; `a` stores and resolves platform commands, but does not manage tmux sessions.
- Drop the separate `--platforms` inspection command for the first implementation. `--which` provides detailed inspection; `--list` provides a compact marker.
- Use `BTreeMap<Platform, CommandType>` rather than `HashMap<String, CommandType>` so output order is stable and persisted platform keys are validated by serde.

## Adversarial Review

Three reviewers critiqued the draft design, then refuted each other's findings. Surviving findings and design responses:

- Base alias overwrite could delete platform variants. Response: `--add` preserves existing `platforms`; variants are removed only through `--platform-remove`.
- Raw string platform keys would allow invalid persisted config. Response: use a serde-validated `Platform` key type.
- GitHub pull bypasses local load/migration. Response: use one shared config-content parser for local load and pull.
- Older config-writing binaries can drop the new `platforms` field. Response: call this out as a residual risk; do not point checked-in config at a missing wrapper in this task.
- The concrete `co`/`cl` goal was under-accepted, and `cor` was undecided. Response: README must document setup commands for `co`, `cor`, and `cl`; checked-in config changes wait for wrapper availability or explicit approval.
- `--which` and `--list` could show the fallback while execution uses an override. Response: both use the active command; `--which` lists default and variants.
- `--platform-add` overwrite behavior was undefined. Response: mirror `--add` prompt/`--force`.
- Parser reuse was underspecified. Response: extract a pure `Result`-returning parser used by both commands.
- Platform execution tests need a non-host-OS seam. Response: add `execute_alias_for_platform` or equivalent testable helper.

Mixed or non-surviving findings:

- A separate `--platforms` command was defensible but unnecessary for the first implementation. The design drops it for lean scope.
- Display helper duplication was not verified against implementation, but the design still centralizes `CommandType` formatting to avoid the risk.

## Residual Risks

- Actual tmux behavior depends on an external wrapper command such as `a-tmux`. This design stores and resolves platform-specific commands; it does not create that wrapper.
- If an older installed `a` binary pulls or saves a config containing `platforms`, it can reserialize the config without that field. This is a known rollout risk outside the dev-sandbox scope.
