# HLD: Move `a` into Deltic tools

Status: DRAFT V1
Date: 2026-06-28

## Intent

Move `a` into the Deltic source tree as a Deltic-built and Deltic-installed fleet tool, while preserving the short local command:

```text
a <alias> [args...]
```

`a` remains the fast alias CLI. Deltic owns the tool's build, install, release pins, and alias-config replication across the fleet.

## Success Looks Like

- A later build run can move the source into Deltic without inventing a new architecture.
- Users still type `a` for alias execution and local alias edits.
- Deltic installs and verifies the `a` binary through the same fleet-tool mechanism used for `mdminder`, `mdkloc`, and `mdemail`.
- Alias config no longer depends on the standalone `0x4D44/a` repo or `a`'s hardcoded GitHub sync.
- Alias config is a Deltic-owned user config artifact that Deltic syncs and materializes to fleet targets.
- Alias execution remains offline and does not require Deltic, GitHub, or network availability once the local config exists.

## Scope

In scope:

- Convert Deltic from a single Cargo package into a workspace using the target layout:

```text
deltic/
  Cargo.toml
  crates/
    deltic-aliases/
    deltic-core/
    deltic-fleet/
    deltic-config/
  apps/
    deltic/
  tools/
    a/
```

- Move the current Deltic app package to `apps/deltic`.
- Move `a` into `tools/a` as a separate executable package with binary name `a`.
- Add a small shared `crates/deltic-aliases` crate for the alias schema, validation, config path resolution, and atomic local store operations.
- Preserve `a`'s alias execution behavior:
  - `std::process::Command`, not shell interpolation.
  - `shell_words` tokenization.
  - Parameter substitution.
  - Platform overrides.
  - Sequential and parallel chain semantics.
  - Saved exit-code conditions.
- Add `a` to Deltic's existing fleet tool catalog and release asset path.
- Add Deltic-owned alias replication and local materialization.
- Define the acceptance criteria a build run must satisfy.

## Non-Goals

- No old-config migration from `~/.alias-mgr/config.json`.
- No old source-history migration.
- No rollback support.
- No staged ops choreography.
- No new environment variables.
- No feature flags.
- No change from `a` to `deltic a` for normal alias execution.
- No semantic conflict resolver for concurrent alias edits. Deltic's existing last-write-wins philosophy is enough for this sandbox.
- No shared fleet alias layer in `deltic-config` in this design. Aliases are treated as user-owned executable config.

## Current Context

Current `a` facts:

- `/Users/md/language/a/Cargo.toml` is a single Rust binary crate named `a`, currently version `1.6.1`.
- Most behavior lives in `/Users/md/language/a/src/main.rs`.
- `a` dispatches management flags such as `--add`, `--remove`, `--list`, `--which`, `--push`, and `--pull`; any other first argument is an alias name.
- Runtime config is currently `$HOME/.alias-mgr/config.json` or `%USERPROFILE%\.alias-mgr\config.json`.
- Sync is hardcoded to GitHub repo `0x4d44/a`, branch `main`, path `config.json`.
- Execution uses `std::process::Command` with inherited stdio and does not invoke an implicit shell.

Current Deltic facts:

- `/Users/md/language/deltic/Cargo.toml` is currently a single package, not a workspace.
- Deltic already distributes helper tools through `apps/deltic/src/fleet/tools.rs` after the workspace move. In today's tree this is `/Users/md/language/deltic/src/fleet/tools.rs`.
- Tool rollout is content-pinned by `fleet/tools.toml` in `deltic-config`.
- Installed tool state is verified by SHA-256, not by parsing `--version`.
- Deltic already has GitHub token, sync-state, rate-limit, and config persistence patterns that should be reused rather than reimplemented in `a`.

## Design

### 1. Workspace Shape

Convert Deltic to a workspace.

The root `Cargo.toml` becomes the workspace manifest. The current Deltic package moves under `apps/deltic`. The new `a` tool package lives under `tools/a`. A small shared alias crate lives under `crates/deltic-aliases`.

The shared alias crate is justified because both the Deltic app and the `a` binary must understand the alias schema:

- `a` must load, validate, edit, and execute aliases.
- Deltic must validate pulled alias config before replacing local files.
- Deltic must materialize the same config to host, WSL, and macOS target paths.

The shared crate must not contain command execution. Execution stays in `tools/a`, where the command-runner tests live.

### 2. Package Responsibilities

`crates/deltic-aliases` owns:

- Alias schema:
  - `Config`
  - `AliasEntry`
  - `CommandType`
  - `CommandChain`
  - `ChainCommand`
  - `ChainOperator`
  - `Platform`
- Schema validation.
- Serialization and deserialization.
- Local path resolution for each target's Deltic config directory.
- Atomic write helpers.
- Malformed-config behavior.

`tools/a` owns:

- The `a` executable.
- The existing short CLI surface for local alias management and execution.
- Command-spec parsing for `--add`, `--platform-add`, and chain operators.
- Alias execution.
- Command runner abstraction and tests.
- User-facing help and concise errors.

`apps/deltic` owns:

- Fleet install and verify for the `a` binary.
- Alias sync against Deltic's existing user config sync source.
- Alias materialization to every target where `a` is installed.
- Manual admin commands:
  - `deltic aliases status`
  - `deltic aliases pull`
  - `deltic aliases push`
- Auto-sync integration for external alias-file edits.

### 3. Local Alias Config

The local alias config moves from the standalone `a` directory to the Deltic config directory:

```text
Windows host: %USERPROFILE%\.deltic\aliases.json
macOS host:   $HOME/.deltic/aliases.json
WSL target:   $HOME/.deltic/aliases.json
```

This makes the config clearly Deltic-owned while keeping a simple local file that `a` can read quickly.

`a --config` prints the new Deltic-owned path.

First run creates an empty alias config only when a write command needs it. Read-only commands do not silently overwrite malformed config.

### 4. Remote Alias Config

Aliases are user-owned executable configuration, not shared fleet prompt/config data. The remote source of truth should therefore use Deltic's personal sync model, not the shared `deltic-config` fleet repo.

Remote path:

```text
<login>/deltic-personal:config/<login>/aliases.json
```

Deltic owns push, pull, status, rate-limit handling, and token resolution. `a` must not keep the old hardcoded GitHub target, old token chain, or old `0x4D44/a` sync path.

### 5. `a` CLI Behavior

Preserve:

- `a --help`
- `a --version`
- `a --config`
- `a --add <name> <command> [options]`
- `a --platform-add <name> <platform> <command> [options]`
- `a --platform-remove <name> <platform>`
- `a --list [filter]`
- `a --remove <name>`
- `a --which <name>`
- `a <alias> [args...]`

Redefine old sync flags:

- `a --push`
- `a --pull`

These should no longer perform GitHub sync from inside `a`. They should be removed from help and return a clear error pointing to Deltic:

```text
Alias sync is managed by Deltic. Use `deltic aliases push` or `deltic aliases pull`.
```

This preserves a useful failure mode without keeping the wrong ownership boundary.

### 6. Alias Execution

Alias execution remains local and offline.

Execution flow:

1. Load local `aliases.json`.
2. Resolve the active command for the current platform.
3. Apply parameter substitution.
4. Split command text with `shell_words`.
5. Execute using `std::process::Command`.
6. Preserve the child exit code for simple commands.
7. Preserve current sequential and parallel chain behavior.

No alias execution path may call:

- GitHub.
- Deltic sync.
- Deltic fleet install.
- A shell, unless the stored alias explicitly names one as the program.

### 7. Deltic Replication

Deltic's alias replication has two jobs:

1. Sync the canonical alias JSON with the personal remote.
2. Materialize that JSON to every local fleet target where `a` runs.

The Deltic app reuses the existing config-sync patterns:

- Startup pull.
- Periodic pull.
- Push after local edits.
- Rate-limit persistence.
- Token resolution through the existing Deltic token provider.
- External-edit detection for the local alias file.

Materialization targets:

- Windows host Deltic config dir.
- Each discovered WSL target's Deltic config dir.
- macOS host Deltic config dir, where applicable.

Pulled remote content must be parsed and validated by `crates/deltic-aliases` before any target file is replaced.

Writes use same-directory temp files plus atomic replace where the platform supports it. A failed write must leave either the old valid file or no file, never a partial JSON file.

### 8. Fleet Tool Distribution

`a` joins the existing fleet tool catalog.

Catalog entry:

```rust
ToolSpec {
    name: "a",
    repo: "0x4D44/deltic",
    post_install: None,
    windows_only: false,
}
```

Ordering:

- `a` is an inert tool.
- It should appear before `mdminder`, because `mdminder` has `post_install: Some("install-hooks")` and must remain last.

Release assets use the existing fleet tool naming contract:

```text
a-v<version>-windows-x86_64.exe
a-v<version>-windows-x86_64.exe.sha256
a-v<version>-linux-x86_64
a-v<version>-linux-x86_64.sha256
a-v<version>-macos-arm64
a-v<version>-macos-arm64.sha256
```

Only publish and pin OS assets that are actually built. Missing per-OS pins remain `NoSource`, following the existing tool behavior.

The first implementation should co-version `a` with the Deltic release tag. Independent per-tool versions can be reconsidered after more tools move in.

## Acceptance Criteria And Test Oracles

Workspace:

- `cargo metadata --workspace` lists `deltic`, `a`, and `deltic-aliases`.
- `cargo fmt --all -- --check` passes.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` passes.
- `cargo test --workspace --all-targets --all-features` passes with stdin closed.
- `cargo build --workspace --release` builds Deltic and `a`.

Alias schema:

- Golden JSON fixtures round-trip without semantic change.
- Invalid platform names fail to load.
- Reserved alias names are rejected.
- Simple aliases, platform variants, chains, parallel chains, and saved exit-code conditions serialize and deserialize correctly.

Local config:

- `a --config` prints the Deltic-owned `aliases.json` path, not `.alias-mgr`.
- `a --add` creates parent directories and writes valid JSON under the Deltic config dir.
- Config writes are atomic: a simulated write failure leaves the previous file intact.
- Malformed local config makes read and execution commands fail with a nonzero exit.
- Read-only commands never replace malformed config with defaults.

CLI behavior:

- Known management flags dispatch to management handlers.
- Unknown `--` flags fail with usage.
- Bare first arguments dispatch to alias execution.
- `a --push` and `a --pull` do not use old GitHub sync and point users to `deltic aliases`.
- `a --list` remains sorted and filterable.
- `a --which` shows default command, active platform command, platform variants, and chain details.

Execution:

- A mock runner proves no shell process is inserted for commands containing `&&`, `||`, `;`, pipes, or quoted arguments.
- An injection oracle such as `rec one; touch sentinel` invokes `rec` with literal args and does not create `sentinel`.
- Parameter substitution covers `$1`, multi-digit arguments, `$@`, `$*`, `$$`, missing args, and quoted args.
- Sequential chains preserve `&&`, `||`, `;`, `--if-code`, `--save`, and `--if-saved` behavior.
- Parallel chains preserve success and failure aggregation.
- Platform override tests prove the current platform command wins over the default.
- Offline execution succeeds when the sync layer is replaced by a panic stub.

Deltic alias sync:

- `deltic aliases status` reports local, remote, and materialized target states.
- `deltic aliases pull` validates remote JSON before replacing any local target file.
- `deltic aliases push` uploads only validated local JSON.
- The remote path is `config/<login>/aliases.json` in the user's `deltic-personal` repo.
- No code path references `0x4d44/a` as the alias sync target.
- Rate-limit state is persisted through the existing Deltic sync-state mechanism.
- External edits to the host alias file are detected and pushed by Deltic's auto-sync path.
- Pull materialization writes host and WSL target alias files atomically.

Fleet tool distribution:

- `apps/deltic/src/fleet/tools.rs::TOOLS` contains `a`.
- `a` appears before hook-bearing `mdminder`.
- A valid `[[tool]] name = "a"` pin reconciles to `Missing`, `Stale`, or `UpToDate` by SHA-256.
- An absent `a` pin is `NoSource`, not an error.
- Install-path tests place `a.exe` under `%LOCALAPPDATA%\Programs\Deltic` on Windows and `a` under `~/.local/bin` on WSL/macOS.
- Release packaging emits the raw `a` assets and matching `.sha256` sidecars.
- The generated `fleet/tools.toml` entry for `a` uses sidecar hashes, not hand-typed hashes.

## Residual Risks

- Workspace conversion is broad path churn. Scripts, tests, `include_str!` paths, assets, and release packaging can break if the move is mechanical but incomplete.
- Alias config is executable authority. The safety boundary is no implicit shell; it is not a claim that aliases are safe.
- Concurrent alias edits from two machines can still race. This design accepts last-write-wins, matching Deltic's existing sync philosophy.
- WSL target edits may not be noticed immediately if the Deltic host app is not running. Manual `deltic aliases push` remains the explicit sync path.
- Co-versioning `a` with Deltic is simple but couples `a` releases to Deltic releases.
- The first build will probably uncover release-script assumptions that the root package is still at repo root.

## Decision Log

- Decision: Keep `a` as a separate binary named `a`.
  - Rationale: aliases are muscle-memory tooling; `deltic a <name>` is the wrong user experience.

- Decision: Move `a` source to `tools/a`.
  - Rationale: `tools/` communicates that this is a user-facing utility owned by Deltic's release train.

- Decision: Add `crates/deltic-aliases`.
  - Rationale: both Deltic and `a` need the same alias schema and validation. Sharing only the model/store avoids coupling Deltic to alias execution.

- Decision: Deltic owns replication; `a` owns local edits and execution.
  - Rationale: this keeps alias execution fast and offline while removing the separate `a` repo as a config-sync owner.

- Decision: Use Deltic's personal sync repo for alias data.
  - Rationale: aliases are user-owned executable config. The shared `deltic-config` repo remains the source for fleet-owned artifacts such as tool pins, prompts, and skills.

- Decision: Remove old direct `a --push` / `a --pull` GitHub sync.
  - Rationale: the hardcoded `0x4D44/a:config.json` path is exactly the repo split this design removes. Manual sync belongs under `deltic aliases`.

- Decision: Use existing fleet tool distribution for the `a` binary.
  - Rationale: Deltic already has content-pinned install/status machinery for helper tools. A second installer would add complexity without value.

- Decision: Co-version `a` with Deltic at first.
  - Rationale: one release train is the point of moving these tools into Deltic. Independent tool versions can be revisited after more tools move in.

- Tie-break: Choose Draft C's replication and testability over Draft A's binary-only move.
  - Rationale: binary consolidation without alias replication misses Arthur's stated goal.

- Tie-break: Choose Draft B's Deltic-owned local path and malformed-config safety over Draft C's old `.alias-mgr` path.
  - Rationale: Deltic should own the alias lifecycle. Preserving the old path is not required in the sandbox.

- Dissent recorded: one judge preferred keeping `a --push` / `a --pull` as Deltic-managed front-ends.
  - Resolution: keep the boundary clearer for V1. `a` reports the Deltic command; Deltic owns sync.
