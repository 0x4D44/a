# HLD: Move `a` into Deltic tools

Status: DRAFT V4
Date: 2026-06-28

## Intent

Move `a` into the Deltic source tree as a Deltic-built and Deltic-installed tool, while preserving the short local command:

```text
a <alias> [args...]
```

`a` remains the fast alias CLI. Deltic owns the tool's build, install, release pins, and alias-config replication. The first build is deliberately incremental: one usable `a` tool in the Deltic workspace, one Deltic-owned alias config path, Windows-host-authoritative alias edits, manual sync, and explicit materialization to read-only target copies.

## Success Looks Like

- Users still type `a` for alias execution.
- Windows host users can edit aliases with `a --add`, `a --remove`, and related management commands.
- Non-host target copies can execute aliases but cannot create hidden competing authorities.
- The Deltic repo builds and tests the `a` binary.
- Deltic installs and verifies `a` through the existing fleet-tool catalog.
- Alias config no longer depends on the standalone `0x4D44/a` repo or `a`'s hardcoded GitHub sync.
- Deltic can manually push/pull a validated alias JSON through the user's personal sync repo and materialize it to local fleet targets.

## Scope

In scope for the first build:

- Convert Deltic to a minimal workspace while keeping the current Deltic package at the repo root.
- Add `tools/a` as a separate executable package with binary name `a`.
- Add a small `crates/deltic-aliases` crate for alias schema, serde, validation, and pure path helpers.
- Move the `a` CLI implementation into `tools/a`.
- Capture a pre-port behavior oracle from the current standalone `a` before moving behavior.
- Preserve `a`'s alias execution behavior:
  - `std::process::Command`, not shell interpolation.
  - Existing `shell_words` tokenization semantics.
  - Existing parameter substitution semantics, with explicit golden tests.
  - Platform overrides.
  - Sequential and parallel chain semantics, including existing exit-code quirks unless intentionally changed with tests.
  - Saved exit-code conditions.
- Add `a` to Deltic's existing fleet tool catalog.
- Add manual Deltic alias sync commands:
  - `deltic aliases status`
  - `deltic aliases pull`
  - `deltic aliases push`
  - `deltic aliases materialize`
- Define precise acceptance criteria for the build run.

Implementation should land in this order:

1. Workspace, `deltic-aliases`, and the `tools/a` port with current behavior preserved.
2. Deltic alias status/sync/materialization commands, still manual only.
3. Fleet tool catalog, release assets, and manifest-generation support for distributing `a`.

Each stage must be green before the next stage starts. The HLD covers all three because the boundary between `a`, alias replication, and fleet rollout is the actual architectural decision.

North-star layout, not required in this first build:

```text
deltic/
  Cargo.toml
  crates/
    deltic-core/
    deltic-fleet/
    deltic-config/
  apps/
    deltic/
  tools/
    a/
    mdkloc/
    mdemail/
    mdminder/
```

The first build leaves the existing Deltic package at repo root to avoid unnecessary path churn. Moving the Deltic app to `apps/deltic` is a later workspace-cleanup requirement, not part of this HLD's implementation scope.

## Non-Goals

- No old-config migration from `~/.alias-mgr/config.json`.
- No old source-history migration.
- No rollback support.
- No staged ops choreography.
- No new environment variables.
- No feature flags.
- No change from `a` to `deltic a` for normal alias execution.
- No daemon auto-sync for aliases in the first build.
- No watcher-driven auto-push for alias config in the first build.
- No shared fleet alias layer in `deltic-config`; aliases are user-owned executable config.
- No semantic conflict resolver for concurrent machine edits. The first build detects dirty, remote-changed, or target-diverged state and refuses unsafe overwrite.

## Current Context

Current `a` facts:

- `/Users/md/language/a/Cargo.toml` is a single Rust binary crate named `a`, currently version `1.6.1`.
- Most behavior lives in `/Users/md/language/a/src/main.rs`.
- `a` dispatches management flags such as `--add`, `--remove`, `--list`, `--which`, `--export`, `--push`, and `--pull`; any other first argument is an alias name.
- Runtime config is currently `$HOME/.alias-mgr/config.json` or `%USERPROFILE%\.alias-mgr\config.json`.
- Sync is hardcoded to GitHub repo `0x4d44/a`, branch `main`, path `config.json`.
- Execution uses `std::process::Command` with inherited stdio and does not invoke an implicit shell.

Current Deltic facts:

- `/Users/md/language/deltic/Cargo.toml` is currently a single package, not a workspace.
- Deltic already distributes helper tools through `/Users/md/language/deltic/src/fleet/tools.rs`.
- Tool rollout is content-pinned by `fleet/tools.toml` in `deltic-config`.
- Current tool pin validation requires `linux_sha256` for any tool with `windows_only: false`.
- Deltic's current release scripts parse the Deltic version from the root `Cargo.toml`.
- Deltic's existing `ConfigSyncService` is phrase/settings shaped; alias sync must not reuse it directly.

## Design

### 1. Minimal Workspace Shape

Use a root package plus workspace shape for the first build:

```toml
[package]
name = "deltic"
...

[workspace]
resolver = "3"
members = [
  ".",
  "crates/deltic-aliases",
  "tools/a",
]
```

This keeps existing Deltic source paths stable while adding first-class workspace packages for `a` and the shared alias model.

`crates/deltic-aliases` is intentionally narrow. It owns:

- Alias schema.
- Serde.
- Validation.
- Pure helpers such as `aliases_path_for_home(home)`.
- Canonical JSON rendering for hashing and sync.
- Golden fixtures used by both Deltic and `a` tests.

It does not own:

- Fleet target discovery.
- GitHub sync.
- Atomic writes.
- Command execution.
- User-facing CLI text.

Those belong to the binaries that perform them.

### 2. Package Responsibilities

`tools/a` owns:

- The `a` executable.
- Alias reads on every target.
- Windows-host-only alias writes for V1.
- Command-spec parsing for `--add`, `--platform-add`, and chain operators.
- Alias execution.
- Atomic writes to the host alias file.
- Command runner abstraction and tests.
- User-facing help and concise errors.

The Deltic root package owns:

- Fleet install and verify for the `a` binary.
- Manual alias push/pull/status/materialize commands.
- Alias sync metadata.
- Windows-host-to-target materialization.
- Release packaging for the `a` assets.
- PATH-shadow detection for installed `a`.

### 3. Local Alias Config

Alias config moves from the standalone `a` directory to the Deltic config directory:

```text
Windows writable host: %USERPROFILE%\.deltic\aliases.json
WSL/Linux target:      $HOME/.deltic/aliases.json
macOS source-built target, no V1 fleet asset: $HOME/.deltic/aliases.json
```

`a --config` prints the Deltic-owned path for the current environment.

First run creates an empty alias config only when a Windows-host write command needs it.

All ordinary commands, including writes, fail on malformed existing config. A malformed file must never be replaced by defaults or by a partially loaded edit. Repair/reset can be a later explicit command.

The old `.alias-mgr/config.json` path is ignored. Tests must prove that an old file alone is not read, migrated, or rewritten.

### 4. Writable Authority And Target Copies

The first build defines one writable local authority:

```text
the Windows host Deltic alias file: %USERPROFILE%\.deltic\aliases.json
```

Windows-host `a` supports:

- `--add`
- `--remove`
- `--platform-add`
- `--platform-remove`
- `--export`

Non-host target `a` supports read/execution commands:

- `--help`
- `--version`
- `--config`
- `--list`
- `--which`
- `--export`
- alias execution

Non-host target write commands fail clearly:

```text
Alias edits are host-authoritative in this Deltic build. Edit on the host, then run `deltic aliases materialize`.
```

This avoids an unrecoverable WSL edit state. Target copies are read-mostly materialized files, not competing authorities.

`a` determines its write role through an internal `AliasRuntimeContext` provider:

- Production Windows builds return `WritableHost`.
- Production Linux and macOS builds return `MaterializedTarget`.
- Tests inject both roles without relying on real WSL, macOS, or fleet state.

The role provider is platform-derived in V1. It does not read environment variables, alias config, fleet config, target inventory, or remote state. Platform identity and write authority are separate concepts: WSL uses the `linux` platform override for execution, but it is still a non-host write target.

`deltic aliases status` still scans target copies. If any target copy differs from the host, status reports target divergence. `deltic aliases materialize` is the only command that overwrites target copies from the validated host file, and it does not touch the remote.

Sync metadata:

- Use alias-specific sync metadata, not the phrase sync state's single remote SHA.
- Store at `%USERPROFILE%\.deltic\alias_sync_state.json` on the Windows host.
- Minimal V1 fields:
  - `remote_sha`
  - `last_synced_local_hash`
  - `last_sync_at`
- Resolve login live from the authenticated Deltic personal-sync identity.
- Reuse global rate-limit state only if it is host-independent; otherwise store alias-specific rate-limit expiry.

### 5. Platform Names And Runtime Mapping

Persisted platform keys are exactly:

- `windows`
- `macos`
- `linux`

`current` is accepted only as CLI input for `--platform-add` / `--platform-remove`; it is resolved immediately before persistence.

Runtime mapping:

- `cfg(windows)` => `windows`
- `cfg(target_os = "macos")` => `macos`
- all other supported Unix/Linux builds, including WSL => `linux`

Invalid persisted platform keys fail to load. Invalid CLI platform names fail before any config write.

### 6. Canonical Hashing

Dirty-state hashing uses canonical alias JSON, not raw file bytes.

Algorithm:

1. Read bytes.
2. Parse as alias config.
3. Validate schema.
4. Serialize with deterministic key order and stable formatting through `crates/deltic-aliases`.
5. Hash the canonical bytes with SHA-256 hex.

Whitespace-only changes and object-key reordering do not create dirty state. Semantic changes do.

The canonical bytes are also the upload payload for `deltic aliases push` and the materialization payload for target copies.

### 7. Remote Alias Config

Aliases are user-owned executable configuration, not shared fleet prompt/config data. The remote source of truth uses Deltic's personal sync model:

```text
<login>/deltic-personal:config/<login>/aliases.json
```

`<login>` must come from Deltic's authenticated personal-sync identity. It must not come from alias config, environment overrides, the fleet config repo, or user-supplied command arguments.

Validate login before path construction using the GitHub login grammar Deltic already accepts for personal sync. Reject empty, slash-containing, dot-dot, non-normalized, or otherwise path-like values before building `config/<login>/aliases.json`.

Pull/push reject owner/path mismatch before reading or writing executable alias config.

Implement a separate `AliasSyncService`. It may reuse these Deltic primitives:

- token resolution
- GitHub REST/GraphQL helpers
- retry classification
- rate-limit persistence
- JSON output helpers

It must not reuse phrase/TOML-specific `ConfigSyncService` behavior such as phrase shrink guards, `AppConfig` validation, or settings/phrases path projection.

### 8. `a` CLI Behavior

Preserve:

- `a --help`
- `a --version`
- `a --config`
- `a --export [path]`
- `a --add <name> <command> [options]`
- `a --platform-add <name> <platform> <command> [options]`
- `a --platform-remove <name> <platform>`
- `a --list [filter]`
- `a --remove <name>`
- `a --which <name>`
- `a <alias> [args...]`

Deprecated sync flags:

- `a --push`
- `a --pull`

These no longer perform GitHub sync from inside `a`. They are omitted from help, parse before loading the alias store, exit nonzero, and print:

```text
Alias sync is managed by Deltic. Use `deltic aliases push` or `deltic aliases pull`.
```

Early parsing matters: a malformed `aliases.json` must not prevent `a --push` or `a --pull` from reaching this guidance.

### 9. Alias Execution

Alias execution remains local and offline.

Before the port moves behavior into Deltic, capture a behavior oracle from the current standalone `a` at commit `d53c9e0ecbb2d455ac1af9dbac3ba22165f30e96`. The oracle must record fixture config, CLI args, runner calls, skipped commands, saved exit-code state, stdout/stderr assertions where useful, and final exit status. Port tests then assert against that captured oracle rather than redefining "current behavior" after the move.

Execution flow:

1. Load local `aliases.json`.
2. Resolve the active command for the current platform.
3. Apply existing parameter substitution semantics.
4. Split command text with `shell_words`.
5. Execute using `std::process::Command`.
6. Preserve the current simple-command child exit-code behavior.
7. Preserve current sequential and parallel chain behavior, including any existing nonzero-chain quirks unless the build explicitly changes them with tests.

No alias execution path may call:

- GitHub.
- Deltic sync.
- Deltic fleet install.
- A shell, unless the stored alias explicitly names one as the program.

Windows `.cmd` and `.bat` files may still introduce shell parsing through Windows process behavior. V1 must either document those as shell-backed wrappers or reject implicit `.cmd`/`.bat` execution unless the alias explicitly names `cmd` or PowerShell. The safer default is to document and test the current behavior rather than silently claim shell-free semantics where Windows does not provide them.

The HLD does not claim that parameter substitution preserves argv boundaries today. It requires golden tests that document the current behavior for arguments with spaces, quotes, semicolons, pipes, and leading dashes. If the build changes that behavior, the change must be explicit and covered by tests.

### 10. Manual Deltic Alias Commands

`deltic aliases status`:

- Reads host alias file.
- Reads alias sync metadata.
- Optionally probes remote status when credentials are available.
- Scans materialized target files.
- Emits human output and JSON.

Status output is structured, not a single overloaded state.

Top-level JSON fields:

```text
local_state       Missing | Malformed | Valid
sync_state        Unsynced | UpToDate | DirtyLocal | RemoteChanged | RemoteUnavailable
target_state      NoTargets | UpToDate | DivergedTargets | TargetErrors
ready_to_push     boolean
ready_to_pull     boolean
ready_to_materialize boolean
local_path
local_hash
remote_sha
remote_path
remote_login
targets[]
```

Target states:

```text
missing
equal
diverged_valid
malformed
unreadable
untrusted_path
write_failed
```

Precedence:

- `local_state = Malformed` makes push, pull, and materialize fail before remote mutation.
- `sync_state = RemoteChanged` makes push fail before upload.
- `sync_state = DirtyLocal` makes pull fail before overwrite.
- `target_state = DivergedTargets` or `TargetErrors` does not block Windows-host push/pull in V4 because non-host targets are not authorities.
- `ready_to_materialize = true` when at least one trusted target is missing, diverged, malformed, unreadable, or previously failed to write.
- `ready_to_materialize = false` when there are no trusted target changes. Untrusted target paths are reported and skipped; they do not make materialization ready because Deltic must never write to them.

`deltic aliases pull`:

- Resolves authenticated personal identity.
- Downloads remote `config/<login>/aliases.json`.
- Parses and validates JSON before any write.
- Computes canonical remote hash.
- Refuses if host file is malformed.
- Refuses if host file is dirty relative to `last_synced_local_hash`.
- Atomically writes the host file.
- Does not write target copies.
- Updates alias sync metadata with the remote SHA and canonical local hash.

`deltic aliases push`:

- Resolves authenticated personal identity.
- Parses and validates host `aliases.json`.
- Computes canonical host hash.
- Fetches current remote SHA before upload.
- Refuses when current remote SHA differs from metadata `remote_sha`.
- Allows first push only when metadata has no `remote_sha` and the remote file is missing.
- Uploads canonical host JSON to `config/<login>/aliases.json`.
- Uses GitHub's content-SHA conditional update/precondition where available.
- Updates alias sync metadata after successful upload.

`deltic aliases materialize`:

- Parses and validates the host file.
- Writes canonical host JSON to trusted target config dirs.
- Does not touch the remote.
- Does not update alias sync metadata.
- Exits nonzero if any trusted target write fails.
- Keeps successful per-target writes; each target write is atomic at the file level.
- Reports failed targets in `targets[]`, so a repeat `materialize` can repair them.

No alias command auto-pushes external file edits in the first build. File watchers may mark alias state dirty later, but remote mutation requires `deltic aliases push` or a future explicit design.

### 11. Target Path Trust

Deltic materializes aliases only to trusted targets discovered by its existing fleet target discovery.

For each target:

- The destination is exactly `<target-home>/.deltic/aliases.json`.
- The target home itself is canonicalized before constructing the destination.
- The parent directory is created if needed, then canonicalized.
- The final alias path must remain under the expected `<target-home>/.deltic` directory.
- Symlink/reparse-point target homes and final paths are rejected.
- Traversal-like or malformed target homes are rejected.
- Writes use same-directory temp files and atomic replacement where supported.

Untrusted target paths are reported in `targets[]` and skipped. They never receive alias content.

### 12. Fleet Tool Distribution

`a` joins the existing fleet tool catalog.

Catalog entry:

```rust
ToolSpec {
    name: "a",
    repo: "0x4D44/deltic",
    post_install: None,
    windows_only: false,
}
```

Ordering:

- `a` is an inert tool.
- It appears before `mdminder`, because `mdminder` has `post_install: Some("install-hooks")` and must remain last.

Current Deltic validation requires a Linux SHA for any non-Windows-only tool. Therefore the first build must produce Windows and Linux `a` assets before pinning `a` for rollout.

Release path:

- Windows release job builds the full Deltic release and `tools/a`.
- Linux release job builds only `-p a -p deltic-aliases`; it must not run the full Deltic workspace because Deltic is not a Linux product target today.
- Both jobs upload raw `a` assets and `.sha256` sidecars as workflow artifacts.
- The final publish job downloads both OS artifacts and attaches all required assets to the GitHub release.
- The publish guard fails if either required `a` sidecar is missing when `a` is in the catalog.

Release assets:

```text
a-v<version>-windows-x86_64.exe
a-v<version>-windows-x86_64.exe.sha256
a-v<version>-linux-x86_64
a-v<version>-linux-x86_64.sha256
```

Optional later:

```text
a-v<version>-macos-arm64
a-v<version>-macos-arm64.sha256
```

macOS remains `NoSource` until a macOS `a` asset and pin exist. A source-built macOS `a` is a non-host target in V1 and must reject write commands.

The first implementation co-versions `a` with the Deltic release tag.

Co-version rule:

- `tools/a/Cargo.toml` version equals root Deltic `Cargo.toml` version.
- `a --version` reads from package metadata, not a hand-maintained string constant.
- Release scripts fail if the `a` package version differs from Deltic's root package version.

Fleet status should also detect command shadowing:

- Windows: `where a`
- WSL/macOS: `command -v a`

If the installed Deltic-managed `a` is not the first resolved command, fleet status reports `Shadowed` with the winning path. Install can still place the tool, but status must not claim the user shell will run it.

## Acceptance Criteria And Test Oracles

Workspace:

- `cargo metadata --workspace` lists `deltic`, `a`, and `deltic-aliases`.
- Root `Cargo.toml` keeps the Deltic `[package]` version.
- Workspace uses `resolver = "3"`.
- `cargo fmt --all -- --check` passes.
- `cargo clippy --workspace --all-targets --all-features -- -D warnings` passes on supported Deltic host targets.
- `cargo test --workspace --all-targets --all-features` passes with stdin closed on supported Deltic host targets.
- Linux CI for the `a` asset runs only `cargo test -p a -p deltic-aliases` and `cargo build --release -p a`.
- Crate graph check:
  - `tools/a` depends on `deltic-aliases`.
  - `tools/a` does not depend on Deltic sync, fleet, or GitHub modules.
  - `deltic-aliases` contains no command execution.

Versioning:

- `tools/a/Cargo.toml` version equals root Deltic package version.
- `a --version` reports that same version from package metadata.
- Release scripts fail on version drift.

Alias schema:

- Golden JSON fixtures round-trip without semantic change.
- Canonical JSON rendering is deterministic.
- Persisted platform keys are limited to `windows`, `macos`, and `linux`.
- CLI input accepts `windows`, `macos`, `linux`, and `current`.
- `current` is resolved before persistence and is never written as a platform key.
- Runtime platform mapping is tested for Windows, macOS, Linux, and WSL-as-Linux through an injected platform provider.
- Invalid platform names fail to load or fail before write, depending on whether they came from persisted JSON or CLI input.
- Reserved alias names are rejected.
- Simple aliases, platform variants, chains, parallel chains, and saved exit-code conditions serialize and deserialize correctly.

Local config:

- Windows-host `a --config` prints the Deltic-owned `aliases.json` path, not `.alias-mgr`.
- With only old `.alias-mgr/config.json` present, `a --list` and `a <alias>` do not read it.
- With only old `.alias-mgr/config.json` present, Windows-host `a --add` writes only `.deltic/aliases.json`.
- Windows-host `a --add` creates parent directories and writes valid JSON under the Deltic config dir.
- The `AliasRuntimeContext` role provider is injectable in tests.
- A Windows/WritableHost role permits write commands.
- Linux, WSL-as-Linux, and macOS/MaterializedTarget roles reject write commands.
- No write-role decision depends on environment variables, alias JSON, fleet config, target inventory, or remote state.
- Non-host `a --add`, `--remove`, `--platform-add`, and `--platform-remove` exit nonzero with the host-authoritative edit message.
- Config writes are atomic: a simulated write failure leaves the previous file intact.
- Malformed local config makes read, write, and execution commands fail with a nonzero exit.
- Read-only commands never replace malformed config with defaults.

CLI behavior:

- Known management flags dispatch to management handlers.
- Unknown `--` flags fail with usage.
- Bare first arguments dispatch to alias execution.
- `a --help` omits `--push` and `--pull`.
- `a --push` and `a --pull` parse before loading the alias store, exit nonzero, print the Deltic handoff message, and invoke no sync backend.
- `a --export [path]` exports the new `.deltic/aliases.json` content and never reads `.alias-mgr`.
- `a --list` remains sorted and filterable.
- `a --which` shows default command, active platform command, platform variants, and chain details.
- A command matrix covers every preserved management flag with initial JSON, command, expected JSON, exit code, and key output.

Execution:

- Pre-port oracle capture from standalone `a` commit `d53c9e0ecbb2d455ac1af9dbac3ba22165f30e96` is checked into the build branch before the port changes behavior.
- Port tests compare against the pre-port oracle rather than newly invented goldens.
- Golden behavior tables cover:
  - alias fixture
  - CLI args
  - expected runner calls
  - expected skipped commands
  - saved-code state
  - final process exit status
- Golden cases include simple command success/failure, sequential chain skip/continue, parallel nonzero-child behavior, saved-code conditions, substitution, and platform override.
- A mock runner proves no extra shell process is inserted for commands containing `&&`, `||`, `;`, pipes, or quoted arguments.
- Windows wrapper behavior is documented and tested for `.cmd` / `.bat` if implicit wrapper execution remains supported.
- An injection oracle such as `rec one; touch sentinel` invokes `rec` with literal args and does not create `sentinel`.
- Parameter substitution covers `$1`, multi-digit arguments, `$@`, `$*`, `$$`, missing args, quoted args, spaces, semicolons, pipes, and leading dashes.

- Platform override tests prove the current platform command wins over the default.
- Execution tests pass with network disabled and without any Deltic sync dependency.

## Residual Risks

- Even a minimal workspace can expose release or tooling assumptions around root-package layout.
- Alias config is executable authority. The safety boundary is no implicit shell; it is not a claim that aliases are safe.
- Windows batch wrappers may invoke shell-like parsing through OS behavior; V1 must document and test the chosen behavior.
- Multi-machine edits can still race. The first build detects dirty/remote-changed state and refuses unsafe overwrite instead of resolving conflicts.
- Non-Windows alias edits are not first-class writers in V1. Write commands fail there; users must edit on the Windows host and materialize.
- Co-versioning `a` with Deltic is simple but couples `a` releases to Deltic releases.
- Linux asset production is required before WSL rollout under current Deltic tool validation.
- A shadowed `a` can still exist on PATH; status detects it, but fixing PATH order remains user/environment work.

## Decision Log

- Decision: Keep `a` as a separate binary named `a`.
  - Rationale: aliases are muscle-memory tooling; `deltic a <name>` is the wrong user experience.

- Decision: Move `a` source to `tools/a`.
  - Rationale: `tools/` communicates that this is a user-facing utility owned by Deltic's release train.

- Decision: Keep the current Deltic package at repo root for the first build.
  - Rationale: it avoids broad `apps/deltic` path churn and prevents immediate breakage in release scripts that parse root `Cargo.toml`.

- Decision: Add only `crates/deltic-aliases` now.
  - Rationale: both Deltic and `a` need the same alias schema and validation. Other future crates are deferred until they remove real duplication.

- Decision: Deltic owns replication; `a` owns Windows-host edits and local execution.
  - Rationale: this keeps alias execution fast and offline while removing the separate `a` repo as a config-sync owner.

- Decision: The Windows host alias file is the writable local authority for V1.
  - Rationale: this avoids undefined multi-target ownership. Target copies are materialized and divergence-checked, not silently merged.

- Decision: `a` uses a platform-derived `AliasRuntimeContext` role provider for V1 write authority.
  - Rationale: Windows Deltic host writes are allowed; Linux, WSL-as-Linux, and macOS are materialized targets. This is implementable without environment variables or Deltic module dependencies and is injectable in tests.

- Decision: Non-host `a` write commands fail in V1.
  - Rationale: allowing non-Windows target writes without an adoption/merge path creates unrecoverable divergence.

- Decision: `deltic aliases pull` writes only the Windows host alias file and sync metadata.
  - Rationale: `deltic aliases materialize` is the single explicit operation that overwrites target copies, which keeps target repair semantics clear and testable.

- Decision: Store alias sync metadata at `%USERPROFILE%\.deltic\alias_sync_state.json`.
  - Rationale: one concrete path is easier to test and avoids leaving a storage fork for the builder.

- Decision: Capture a pre-port behavior oracle from standalone `a` commit `d53c9e0ecbb2d455ac1af9dbac3ba22165f30e96`.
  - Rationale: preserving current behavior needs an independent oracle taken before the port, not tests written after behavior has moved.

- Decision: `deltic aliases push` must fetch and compare remote SHA before upload.
  - Rationale: executable alias config must not silently clobber another machine's remote edit.

- Decision: Use Deltic's personal sync repo for alias data.
  - Rationale: aliases are user-owned executable config. The shared `deltic-config` repo remains the source for fleet-owned artifacts such as tool pins, prompts, and skills.

- Decision: Implement `AliasSyncService`, not direct `ConfigSyncService` reuse.
  - Rationale: phrase/settings sync is TOML and phrase-specific. Alias sync is JSON and needs its own validation and dirty-state rules.

- Decision: Remove old direct `a --push` / `a --pull` GitHub sync.
  - Rationale: the hardcoded `0x4D44/a:config.json` path is exactly the repo split this design removes. Manual sync belongs under `deltic aliases`.

- Decision: Keep `a --export`, retargeted to the new Deltic-owned alias path.
  - Rationale: export is useful local inspection and does not violate Deltic sync ownership.

- Decision: Use existing fleet tool distribution for the `a` binary.
  - Rationale: Deltic already has content-pinned install/status machinery for helper tools. A second installer would add complexity without value.

- Decision: Publish Windows and Linux `a` assets before pinning `a` as a non-Windows-only tool.
  - Rationale: current Deltic pin validation requires Linux SHA for non-Windows-only tools. This avoids a manifest entry that installs nowhere.

- Decision: Co-version `a` with Deltic at first.
  - Rationale: one release train is the point of moving these tools into Deltic. Independent tool versions can be revisited after more tools move in.

- Tie-break: Choose Draft C's replication and testability over Draft A's binary-only move.
  - Rationale: binary consolidation without alias replication misses Arthur's stated goal.

- Tie-break: Choose Draft B's Deltic-owned local path and malformed-config safety over Draft C's old `.alias-mgr` path.
  - Rationale: Deltic should own the alias lifecycle. Preserving the old path is not required in the sandbox.

- Tie-break: Scale V2/V4 down from daemon auto-sync to manual alias sync/materialization.
  - Rationale: the first build should establish correct ownership and testable sync semantics before adding watchers or periodic automation.

- Dissent recorded: one judge preferred keeping `a --push` / `a --pull` as Deltic-managed front-ends.
  - Resolution: keep the boundary clearer for V1. `a` reports the Deltic command; Deltic owns sync.
