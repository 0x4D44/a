## Phase 1 - Understand

Ran three read-only reader agents plus a local source pass.

Current `a` facts:
- `a` is a single Rust binary crate, version `1.6.1`.
- Most behavior lives in `src/main.rs`.
- The command surface uses management flags (`--add`, `--remove`, `--list`, `--which`, `--push`, `--pull`) and treats any other first arg as an alias name.
- Alias execution uses `std::process::Command`, not shell interpolation, with `shell_words` splitting and inherited stdio.
- Runtime config is currently `$HOME/.alias-mgr/config.json` or `%USERPROFILE%\.alias-mgr\config.json`.
- GitHub sync is hardcoded to `0x4d44/a`, branch `main`, path `config.json`.

Deltic facts:
- Deltic is currently a single Rust package, not a Cargo workspace.
- Existing Deltic fleet tools are managed by `src/fleet/tools.rs` using a static catalog plus `fleet/tools.toml` content pins from `deltic-config`.
- Tools install to Deltic's install dir on Windows and `~/.local/bin` on WSL/macOS; status compares installed SHA-256 to the manifest pin.
- The release path currently needs explicit work to emit raw tool assets and sidecar hashes for in-repo tools.
- Deltic already has GitHub sync, rate-limit, token, and config-layering machinery, but aliases should have their own small store and oracles rather than being folded into phrases.

Design implications:
- The build should convert Deltic to a workspace with a top-level `tools/a` package and likely a small shared alias crate.
- Keep the `a` executable as the user-facing command.
- Remove or replace `a`'s bespoke hardcoded GitHub sync with Deltic-owned alias config replication.
- Keep one tool distribution mechanism: Deltic's existing fleet tool catalog and pinned raw release assets.

- Alias data should use Deltic's personal sync repo path rather than the shared `deltic-config` repo because aliases are user-owned executable config.

## Phase 3 - Adversarial review round 1

Ran a mixed review team:
- correctness
- simplicity / over-engineering
- testability
- security
- devil's advocate

The round found critical issues. Ran 3 skeptic verification votes. Findings confirmed by at least 2 of 3:
- Multi-target alias ownership was undefined and could lose WSL/stopped-Deltic edits.
- The fleet-tool pin plan was invalid under current Deltic validation: a non-Windows-only tool needs a Linux SHA.
- Release packaging did not define Linux/macOS `a` asset production.
- Workspace layout was over-scoped by naming future crates not used in the design.
- Alias sync needed to be a separate service, not direct phrase/config sync reuse.
- Release scripts that parse the root `Cargo.toml` needed explicit handling.
- External edit auto-push was too risky/too much for V1.
- Remote provenance needed authenticated-login wording.
- Parameter substitution needed explicit argv-boundary/golden tests.
- Behavior preservation needed golden runner-call/exit-status tables.
- Alias sync needed fake remote/target test seams.
- V1's daemon auto-sync scope was too large for the first build.

Revised V2:
- Kept the current Deltic package at repo root and added a minimal workspace.
- Limited new shared crate to `crates/deltic-aliases`.
- Defined the host alias file as the first-build writable authority.
- Made WSL/mac target copies materialized/read-mostly with divergence detection.
- Replaced daemon auto-sync with manual `deltic aliases status|pull|push|materialize`.
- Required alias-specific sync metadata.
- Required a separate `AliasSyncService`.
- Required Windows and Linux `a` assets before pinning `a` as non-Windows-only.
- Added precise status states, fake sync seams, crate-graph checks, old-path ignored tests, and golden behavior tables.

## Phase 3 - Adversarial review round 2

Reviewed V2 with the same mixed lenses. The critical finding was that
`deltic aliases push` could still overwrite a newer remote alias file because the
push flow did not fetch the current remote content SHA immediately before upload.

Other material findings:
- The status model needed independent local, sync, and target state fields rather
  than one collapsed enum.
- Non-host writes were still ambiguous; target copies needed to be read/execution
  only in the first build.
- The Linux `a` asset path needed to be concrete enough to satisfy existing
  fleet-tool manifest validation.
- Co-versioning needed a testable rule because standalone `a` currently has a
  hardcoded version constant.
- Target materialization needed path-trust rules.
- Sync/status output needed redaction rules.
- Fleet status needed to detect a shadowed old `a` on PATH.
- The deltic-config tool manifest generator needed an explicit `a` input path so
  regeneration does not drop the new tool entry.

Revised V3:
- Made the host alias file the only writable authority for V1.
- Made non-host `a` write commands fail with a clear host-authoritative message.
- Split alias status into local, sync, and target state fields.
- Required push to fetch and compare the current remote SHA before upload.
- Added canonical hashing rules for semantic dirty checks.
- Added target path-trust checks and atomic same-directory writes.
- Made the Linux asset production and manifest-generation contract explicit.
- Added `resolver = "3"`, version drift checks, shadowed-PATH detection, and
  redaction acceptance criteria.

## Phase 3 - Adversarial review round 3

Reviewed V3 with correctness, simplicity, testability, security, and devil's
advocate lenses.

No reviewer found a security critical. Simplicity and testability found no
criticals, but did raise high-signal gaps around scope, role test seams,
pre-port behavior oracles, and missing `ready_to_materialize` output.

Correctness and devil's advocate found two critical blockers:
- Target overwrite semantics conflicted: `pull` materialized trusted target
  copies, while target acceptance criteria said diverged/malformed targets were
  overwritten only by explicit `deltic aliases materialize`.
- Host/non-host write authority was not implementable: V3 required `a` to reject
  non-host writes but did not define the predicate or trusted source for the
  host/target decision. The macOS wording was also inconsistent.

Ran three skeptic verification votes. All three confirmed both criticals.

Revised V4:
- Made V1 write authority Windows-host-only.
- Added an injectable `AliasRuntimeContext` role provider: Windows production
  builds are `WritableHost`; Linux, WSL-as-Linux, and macOS are
  `MaterializedTarget`.
- Defined platform names separately from write authority.
- Made `deltic aliases pull` write only the Windows host alias file and sync
  metadata.
- Made `deltic aliases materialize` the only command that overwrites target
  copies.
- Added `ready_to_materialize` to status JSON and acceptance criteria.
- Added partial materialize failure semantics.
- Required a pre-port behavior oracle from standalone `a` commit
  `d53c9e0ecbb2d455ac1af9dbac3ba22165f30e96`.
- Chose `%USERPROFILE%\.deltic\alias_sync_state.json` as the alias sync metadata
  path.

## Phase 3 - Adversarial review round 4

Reviewed V4 with the same mixed lenses.

Resolved from round 3:
- The pull/materialize target overwrite conflict was resolved: pull wrote only the
  host file, and materialize was the only target overwrite operation.
- The previous host/non-host predicate was made testable, but it still leaned too
  much on platform.

Round 4 findings:
- Correctness found a critical first-pull ambiguity. With no alias sync metadata
  and an existing valid local alias file, V4 did not say whether `pull` could
  overwrite the local file.
- Devil's advocate found a critical ambiguity in "Windows host": a platform-only
  writer rule made every Windows install a writer while the text still claimed
  one writable local authority.
- Security found a high sign-off risk around `.cmd` / `.bat` wrappers: V4 could
  not both claim no implicit shell and allow wrapper execution by documentation.
- Devil's advocate also found high issues around non-persisted materialization
  failure state and target path TOCTOU checks.

Ran three skeptic verification votes:
- First-pull ambiguity was confirmed critical by all three.
- Windows-host ambiguity was confirmed critical by two and downgraded by one; the
  majority was treated as binding.

Revised V5:
- Replaced platform-derived writer authority with Deltic-installed
  `a_runtime_context.json`.
- Defined `native_writer` and `materialized_target` roles. Source-built or
  unmarked copies fail closed as materialized targets.
- Made native Deltic hosts explicit writers in a multi-writer model; materialized
  targets are read-only.
- Added first-pull refusal when sync metadata is missing and local valid alias
  data is non-empty.
- Rejected implicit Windows `.cmd` / `.bat` execution unless the alias explicitly
  names a shell.
- Removed persisted materialization-failure assumptions; status re-derives target
  state from the filesystem.
- Required target parent identity revalidation/no-follow semantics, skipping
  targets as untrusted when safe checks are unavailable.

## Phase 3 - Adversarial review round 5

Reviewed V5 with the mixed review team.

No critical findings from correctness, simplicity, testability, or security.
Devil's advocate found one critical: first-sync deadlock. V5 refused pull when
local data was non-empty and metadata was missing, while first push was allowed
only when the remote was missing. If local and remote canonical JSON were equal
but metadata was lost, neither command could establish a baseline.

Ran three skeptic verification votes. All three confirmed the first-sync
deadlock as critical.

Material high findings folded into the next draft:
- Runtime context should be described as a same-user local role marker, not a
  tamper-proof security boundary.
- `.cmd` / `.bat` rejection needs resolver tests for PATHEXT, extensionless,
  relative, absolute, and case-varied paths.
- `ready_to_*` booleans need explicit truth-table tests.
- Push must require GitHub content-SHA preconditions and test a fetch/upload
  race.
- WSL materialization must remain an acceptance requirement; same-user symlink
  races after parent revalidation are out of V1 scope.

Revised V6:
- Added equal-canonical-hash baseline adoption for missing sync metadata.
- Kept first-sync refusal when local and remote valid data differ.
- Made GitHub content-SHA preconditions mandatory for push updates.
- Clarified runtime context as local role state, not a security boundary.
- Added resolver, readiness, race, and WSL materialization acceptance criteria.
